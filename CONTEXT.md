# Domain Context

This glossary defines Sóþspell's domain language. It deliberately avoids storage
and implementation details. Use these terms consistently in code, tests, docs,
plans, prompts, and UI copy.

## Glossary

### Sóþspell

A versioned, portable walkthrough of one software project at one revision. A
sóþspell is the artifact the player plays: chapters, beats, code anchors,
diagrams, narration, and metadata. It is not a chat transcript, a wiki, or a
video file. The word is Old English for "truth story"; the ASCII slug used in
code and URLs is `sothspell`.

### Truth story

The property a sóþspell must have: its claims about the project are grounded in
the project snapshot and can be traced to code. A beautiful explanation that
cannot be traced is not a truth story.

### Project

The software repository being explained. A project has a name, a local root, a
revision, and a snapshot. The first project is Bunbun. A project is read-only
from Sóþspell's point of view.

### Project snapshot

An immutable, content-addressed view of a project at a revision. A snapshot
contains the file manifest, hashes, languages, symbols, dependency graph, docs,
and warnings. Authoring and playback resolve anchors against a snapshot; they do
not read the working tree on every request.

### Revision

The identity of the project state a snapshot represents: commit, branch, and
whether the working tree was dirty. A revision is part of the snapshot and the
tour metadata. A tour is pinned to one revision.

### Symbol

A named declaration the analyzer can find in the source: a module, class,
method, property, function, variable, interface, type, enum, namespace, or
object. A symbol has a stable ID, a source range, an export flag, and optional
decorators. A symbol is the primary anchor target for a tour.

### Project brief

A deterministic, structural summary of a project snapshot: workspace packages,
applications, entry points, feature modules, docs, plans, Prisma models, and
graph statistics. A project brief is what the authoring pipeline reads first; it
is not generated by a model.

### Feature module

A top-level domain directory under an application's source tree, such as
`apps/api/src/comments`. A feature module groups files and symbols for the
project brief; it is a navigation aid, not a claim that every directory is a
NestJS module.

### Analysis cache

The per-file store of parsed symbols and imports, keyed by analyzer version,
path, language, content hash, and redaction state. The cache speeds up repeat
analysis; it never changes the snapshot ID for unchanged content.

### Chapter

A narrative unit of a sóþspell. A chapter has a title, a summary, one or more
diagrams, and an ordered set of beats. Chapters give the story its top-level
shape; they are not folders or source directories.

### Beat

The atomic unit of playback. A beat has one idea, one narration passage, one
stage state (code focus and/or diagram focus), an estimated duration, and
optional suggested questions. A beat is the smallest thing a user can pause on,
seek to, or deep-link to.

### Stage

The visual area of the player where code and diagrams appear together. The stage
is driven by the beat's focus, not by arbitrary layout instructions from the
model.

### Code anchor

A stable reference to evidence in the project: a file path, a symbol when
available, a line range hint, and a content hash. The compiler resolves the
symbol first, then the line hint, and verifies the hash. An anchor is how a beat
cites code.

### Code page

A read-only page that shows a project file with the anchored lines highlighted.
A code page carries the repository path, symbol breadcrumb, the originating beat,
and a stale badge when the source no longer matches the anchor hash. Code pages
are shareable deep links, not an editor.

### Diagram instruction

A structured specification for a diagram: kind, title, nodes, edges, groups, and
optional anchor links. A diagram instruction is not HTML, SVG, Mermaid, or a
screenshot. The compiler lays it out deterministically, and the player renders
it.

### Diagram focus

The subset of a diagram's nodes and edges that a beat highlights. Focus changes
animate; the diagram's underlying layout does not change between beats in the
same chapter.

### Narration

The spoken and written explanation of a beat. Narration has text, optionally
aligned audio, sentence timings, and word timings. Text is always available;
audio is optional.

### Sentence timing

The start and end of one sentence within a beat's narration. Sentence timing
drives captions and coarse highlighting.

### Word timing

The start and end of one word within a beat's narration. Word timing drives
fine-grained highlighting in narrated mode. Word timing is derived from a
provider's character alignment when cloud audio is used, or from browser
boundaries when browser speech is used.

### Playback mode

The user's chosen relationship to narration:

- **Read mode** — text and diagrams, auto-advancing at a reading-speed estimate.
- **Listen mode** — speech, synchronized text, and diagrams.
- **Explore mode** — paused; the user controls code, diagrams, and questions.

Mode is not the same as pause state. A user can pause in any mode.

### Run

One user's progress through one sóþspell. A run records the current beat, offset,
completed beats, playback mode, speed, question history, and timestamps. A run is
not part of the sóþspell artifact; it belongs to the user and can be exported or
deleted.

### Interlude

A question and answer inserted into a run without changing the sóþspell. An
interlude pauses playback, preserves the position, and returns to the same frame
when the user continues.

### Guide

The LLM-backed narrator and answerer. The guide authors the tour through the
authoring pipeline and answers questions through the ask pipeline. The guide is
an implementation detail of the product, not a character in the fiction.

### Authoring pipeline

The process that turns a project snapshot into a sóþspell: curriculum planning,
context packing, beat and diagram generation, validation, repair, and quality
reporting. It is not the player and does not run during playback.

### Context pack

The bounded evidence a guide may cite while authoring: the project brief,
anchor candidates with short excerpts and hashes, docs, and supporting metadata.
A context pack never contains a whole file and never contains a redacted file.

### Tour plan

The curriculum the guide proposes before any chapter is written: title,
subtitle, audience, and 3–8 chapters with a goal, a beat budget, and a coverage
checklist. A tour plan is validated before chapter generation.

### Chapter draft

The guide's structured output for one chapter: a diagram instruction and 2–5
beats, each citing anchor candidate IDs and optional diagram focus IDs. A chapter
draft is validated and repaired before it can be assembled.

### Quality report

The record produced beside a generated sóþspell: planned versus written
chapters, beat and anchor counts, dropped chapters, validation issues, estimated
duration, model calls, cache hits, token usage, model ID, and prompt version.

### Publisher

The person or process that generates and reviews a sóþspell. In the first release
the publisher is the local user; the authoring pipeline is their tool.

### Golden tour

A checked-in sóþspell used as a demo and regression fixture. The first golden tour
explains Bunbun at commit `9fef24d`. It is pinned, attributed, and never written
back into the Bunbun tree.

### Stale tour

A sóþspell whose anchor hash no longer matches the current project source. A
stale tour still plays, but affected beats show a stale badge and the code page
explains the mismatch. Staleness is visible, not silently ignored.

### Deep link

A URL that opens a specific beat, code page, or run position. Deep links are part
of the product contract: they survive reloads and can be shared on the same
machine or deployment.

### Progress

The recorded state of a run: current position, completed beats, mode, speed, and
questions. Progress is local-first and anonymous in the first release.

### Harness adapter

The integration layer that lets a host application (the web app, OpenCode, or a
future agent harness) use Sóþspell's core. A harness adapter supplies the project
root, revision, model access, storage, player launch, and progress events. It
does not reimplement authoring or playback.

### Read-only

The rule that Sóþspell may read a project but never write to it or execute its
code. Snapshots, tours, audio, logs, and runs live under Sóþspell's own data
directory. Read-only is a product promise and a test invariant.

## Next-stage terms

These terms are part of the shipped next stage (Phases 9–16) and are binding.

### Connection profile

A named, user-owned configuration for one provider connection: an authoring
model, a narration voice, or another capability. It records the provider, base
URL, model or voice id, output format, and a secret reference. One profile per
kind is active; environment variables remain the fallback.

### Secret reference

An opaque pointer to a stored credential. A secret value never appears in an API
response, a log line, a snapshot, or a sóþspell.

### Imported project

A project cloned from a public Git URL into `SOTHSPELL_HOME`, marked read-only
and analyzed like a local checkout. An imported project records its source URL
and revision; it is never written to and its code never runs.

### Workspace account

A GitHub-backed identity that owns runs, reviews, and preferences across
devices. A run may stay anonymous; an account is optional and local-first use
does not require one.

### Review session

A human review of one generated sóþspell revision: per-beat comments, beat
edits, regeneration, anchor re-verification, and an approve or reject decision.
A review session records the reviewer and the decision; it never changes the
sóþspell silently.

### Translation

A locale-specific rendering of a sóþspell's human-facing strings: narration,
titles, suggested questions, and diagram labels. A translation shares ids,
anchors, paths, and line ranges with its source and never translates code or
identifiers.

### Locale

The language of a sóþspell's narration, UI copy, and narration voice. Anchors
and code are language-independent; a tour declares its source locale and each
translation declares its target locale.

### Embed bundle

A self-contained player build plus one sóþspell's compiled data that a
documentation site can serve without the Sóþspell server. An embed bundle
contains excerpts and narration, never the full repository, and never provider
secrets.

## Canvas terms (v3)

These terms describe the planned canvas era (Phases 17–20) and are binding once
the phase lands.

### Canvas view

An opt-in playback layout that places the home diagram, code containers, and
their links on one pannable, zoomable board. A canvas view presents one beat; it
does not change the sóþspell or the run.

### Canvas scene

The data model of one canvas view: diagram cards, code containers, links,
selection, viewport, and preferences. A canvas scene contains no rendered
markup.

### Diagram card

A movable card that presents one diagram. The beat's diagram is the home card;
other diagrams from the chapter may be added as satellite cards.

### Code container

A movable card that presents one code anchor or one symbol definition: its
symbol, path, line range, excerpt, and actions. A code container is a view of
evidence, not an editor.

### Evidence link

A link that connects one diagram object to the anchor's start line or cited range.
An evidence link carries one citation and no inferred relationship.

### Flow link

A link between two code containers. A flow link carries one relation kind
(`calls`, `references`, or `imports`) and one confidence (`syntax` or `import`).

### Relation index

A symbol-level graph derived from one project snapshot. The relation index
records calls, references, and imports; it never executes project code.

### Project record

A local record of one project's source root, source kind, and revision. A project
record is not part of a snapshot, a sóþspell, or an export; it lets the viewer
resolve source for relations and code pages while keeping absolute paths out of
shareable artifacts.

### Symbol target

A stable symbol ID attached to a diagram object or code anchor. A symbol target
lets the canvas open a definition even when the current beat does not cite that
symbol.

### Canvas outline

The semantic text equivalent of a canvas scene: diagrams, objects, code
containers, relationships, and actions in reading order. The canvas outline is
the screen-reader path and the compact-layout path.

### View preference

A local browser preference for canvas behaviour: auto-zoom, auto-arrange, follow
beat, reduced motion, contrast, palette, or text scale. A view preference is not
a connection profile and does not sync through an account.

### Compact canvas

The vertical list presentation below 768 px. A compact canvas uses the same
scene and actions as the spatial canvas, with links rendered as text.

### Auto-zoom

The optional viewport change that frames a newly opened code container with its
source. Auto-zoom is undoable and can be disabled from its first-run message.

### Auto-arrange

The optional deterministic placement of containers after one is opened.
Auto-arrange is undoable and can be disabled from its first-run message.

## Relationships

- A project has many snapshots; a snapshot belongs to one project and one
  revision.
- A snapshot contains many files, symbols, packages, docs, and graph edges.
- A symbol belongs to one file in one snapshot; a code anchor resolves to one
  symbol or file range.
- A project brief summarizes one snapshot.
- A sóþspell belongs to one project snapshot and contains many chapters.
- A chapter contains many beats and one or more diagrams.
- A beat belongs to one chapter and has one or more code anchors.
- A code anchor belongs to one beat or diagram node and resolves against one
  snapshot.
- A diagram belongs to one chapter; a beat focuses a subset of its nodes and
  edges.
- A narration belongs to one beat; a beat may have no narration audio.
- A run belongs to one user (anonymous in the first release) and one sóþspell.
- A run contains zero or more interludes.
- An interlude belongs to one run and one beat; it does not modify the sóþspell.
- A harness adapter presents a sóþspell and a run; it does not own either.
- A golden tour is a sóþspell with a pinned revision and reviewed evidence.
- A connection profile belongs to one user and one capability kind; at most one
  profile per kind is active.
- An imported project is a project; it has snapshots and a revision like any
  other project.
- A workspace account owns zero or more runs, reviews, and profiles; a run may
  have no account.
- A review session reviews one sóþspell revision and contains comments and one
  decision.
- A translation belongs to one sóþspell and one target locale; it shares anchors
  with its source.
- An embed bundle contains one sóþspell and one player build.
- A canvas view presents one beat and zero or more diagram cards and code
  containers.
- A diagram card presents one diagram; a diagram object may cite one symbol
  target.
- A code container presents one code anchor or one symbol definition.
- An evidence link connects one diagram object to the anchor's start line or
  cited range.
- A flow link connects two code containers and records one relation kind and
  confidence.
- A relation index belongs to one project snapshot and resolves symbol targets
  for that snapshot.
- A project record belongs to one project and points at its local source root; it
  is not part of a snapshot, tour, or export.
- A view preference belongs to one browser, not to an account.
- A canvas outline is the text equivalent of one canvas scene.

## Invariants

1. A beat always has a title, narration text, and a stage.
2. Every code claim in a beat is supported by at least one code anchor, except
   beats explicitly marked as orientation.
3. Every anchor resolves to a real file and, when a symbol is named, a real
   symbol in the snapshot.
4. A tour never contains executable code, raw HTML, or raw SVG from the model.
5. A run never changes the sóþspell it plays.
6. A project is never modified by analysis, authoring, playback, or plugin use.
7. A stale anchor is visible to the user; it is never silently shown as current.
8. Text mode is complete: disabling narration does not remove content.
9. Progress survives a reload; a saved run is never lost because the server is
   temporarily unavailable.
10. A harness adapter uses the same sóþspell format and the same run model as the
    web app.
11. A secret value never appears in an API response, a log, a snapshot, or a
    sóþspell.
12. An imported project is read-only and its code never executes.
13. A translation never changes anchor ids, paths, line ranges, or identifiers.
14. An embed bundle contains excerpts and narration, never the full repository
    and never provider secrets.
15. A canvas view never changes the sóþspell or the run it presents.
16. An evidence link exists only when an anchor cites the target; the canvas
    never invents a citation.
17. A flow link records the relation kind and confidence the relation index
    proved; the canvas never presents an import or reference as a call.
18. Every spatial canvas action has a keyboard path and a canvas-outline
    equivalent.
19. The canvas never reads project files directly; relation evidence comes
    through the bounded API.
20. A canvas export contains only the visible tour excerpts and narration, never
    the full repository or a secret.
21. Canvas is opt-in until the performance and accessibility gates pass; the
    embed stays on the Stage.
22. A project record's source root never enters a snapshot, a sóþspell, or an
    export.
